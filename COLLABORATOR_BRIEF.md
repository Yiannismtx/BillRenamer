# BillRenamer — Collaborator Brief

Paste this whole file into your Claude Code session as context. It describes the
project, every external system it touches, and the exact processes we follow so
nothing breaks for our users.

## What the app is

BillRenamer is a native macOS app (Swift + SwiftUI, macOS 13+, no third-party
runtime deps besides Sparkle) that renames business/accounting PDFs using
Anthropic's Claude API. The user picks a folder; every top-level PDF not
already named correctly is uploaded to Claude, which returns issuer, issue date, a
document type code, and a document number. The file is renamed in place to:

```
YYYYMMDD_Issuer_TYPE_Number.pdf     e.g. 20260830_Vodafone_INV_55484.pdf
```

TYPE is exactly one of: INV (invoices/bills/expenses), PKL (packing list),
CNT (contracts), PAY (payments), CRE (credit notes), TAX (taxes),
LET (letters, mainly to banks), IMP (import/supplier invoices).

Files already matching this pattern are skipped (no API call). Files named by
older format generations are migrated: the two most recent old schemes are
rearranged locally for free; anything older is re-scanned through the API.

  secrets, keys, or personal documents).
- `Sources/BillRenamer/` — all app code:
  - `AppModel.swift` — folder scanning, filename regexes, migrations,
    sanitization, rename loop, per-file statuses.
  - `ClaudeClient.swift` — Claude Messages API call (PDF as a base64 document

  - `Keychain.swift` — API key storage in the macOS Keychain.
  - `ContentView.swift` / `SettingsSheet.swift` / `WhatsNewSheet.swift` — UI.
  - `Updater.swift` — Sparkle auto-update wiring.
- `Resources/Info.plist` — bundle metadata + Sparkle feed URL + public key.
  The version fields are stamped by the release process; don't edit them by hand.
- `build.sh` — builds `BillRenamer.app` (SPM build + manual bundle assembly +
  Sparkle.framework embedding + ad-hoc codesign).
- `release.sh` — local release script (works only on Yiannis's Mac; see below).
- `releases/` — published zips + `appcast.xml`. **Never edit this folder by
  hand** — it is generated by the release process and installed apps consume it.
- `.github/workflows/release.yml` — the release workflow you will use.

## External systems

1. **Anthropic Claude API** (model `claude-sonnet-5`, changeable in the
   app's settings). Each user supplies their own API key from
   https://console.anthropic.com/settings/keys — billed per use, separate from
   any claude.ai subscription. It lives in that user's macOS Keychain,
   never in the repo or the app bundle. For your own testing, make your own key.
   Every scanned PDF is uploaded to Anthropic, so never test with documents you
   wouldn't send there.
2. **GitHub** — source of truth for code AND the update feed. Installed apps
   poll `https://raw.githubusercontent.com/Yiannismtx/BillRenamer/main/releases/appcast.xml`
   via Sparkle. Note: raw.githubusercontent.com caches for ~5 minutes, so a
   just-published release can 404/serve stale briefly — wait, don't re-release.
3. **Sparkle 2** (auto-update framework, pulled via Swift Package Manager) —
   apps check the appcast on launch. Updates must be EdDSA-signed; the private
   key exists in Yiannis's Keychain and in the repo's `SPARKLE_PRIVATE_KEY`
   Actions secret. An unsigned or wrongly signed update is REJECTED by
   installed apps — you cannot ship anything by editing `releases/` manually,
   you'll only break the feed.
4. **GitHub Actions** — builds and publishes releases on GitHub's macOS
   runners. This is how you release (no Mac required).

## How to work (the process)

1. **Always `git pull` before starting.** Releases commit to `main`
   (version bump + zips + appcast), so the branch moves even when no one wrote
   code. Push conflicts are almost always a forgotten pull.
2. Make changes on `main` (or a branch + PR if the change is big). Build and
   test locally if you're on a Mac: `./build.sh` then `open BillRenamer.app`.
3. Keep changes consistent with what's there: statuses flow through
   `FileStatus`, all filename logic stays in `AppModel`, user-visible strings
   get tooltips/help text updated alongside.
4. **If you change the filename format** (avoid unless agreed): you must update
   the `alreadyRenamedRegex`, add a migration regex for the previous scheme,
   and test all format generations against each other for ambiguity. Look at
   the existing `migratedName(from:)` implementations first.
5. Never log, print, or commit API keys. Never touch `releases/` or
   `Resources/Info.plist` version fields manually.

## How to release an update

1. Add an entry for the new version at the TOP of `ReleaseNotes.entries` in
   `Sources/BillRenamer/WhatsNewSheet.swift` (2–4 short user-facing bullets).
   The release fails without it — this is deliberate. These notes appear in the
   in-app "What's New" sheet after users update.
2. Commit and push that along with your changes.
3. On GitHub: **Actions tab → "Release" workflow → Run workflow → enter the
   version** (semantic, always increasing: 1.8.0 → 1.9.0 → …). Green button.
4. The workflow builds the app, signs the zip with the Sparkle key, regenerates
   `appcast.xml`, and pushes to `main`. Takes a few minutes. Every installed
   copy is offered the update on its next launch — users do nothing.
5. If the run fails, read the failed step's log; nothing half-ships (the
   commit+push is the last step). After any release, `git pull` locally.

Coordinate before releasing: agree on who cuts a given release, don't run two
releases at once, and never re-use or decrease a version number — Sparkle
compares versions to decide what's newer.

## Distribution to new users

The app is not notarized (no Apple Developer account — intentional, it's shared
with a few known people). New users: download
`releases/BillRenamer-<latest>.zip` from the repo, unzip, **move the app to
/Applications** (required — macOS "translocation" breaks self-updating when run
from Downloads), right-click → Open the first time to pass Gatekeeper, then
follow the in-app instructions to create and save their Anthropic API key.

**The app must live in /Applications.** Running it from the Desktop, Documents,
or any other iCloud-synced folder breaks auto-updates: iCloud stamps
`com.apple.FinderInfo` onto Sparkle's nested `Installer.xpc`, invalidating its
signature, and macOS then refuses to launch it — updates download but never
install, with no visible error. The `BillRenamer.app` left in the repo by
`build.sh` is a packaging artifact, not the copy to use.

## Known gotchas

- Dates on Greek documents are day-first; the prompt handles this and the app
  rejects extracted years outside [earliest expected year .. next year] as
  suspected misreads (flagged red, file left untouched) — keep that guard. The
  floor defaults to 2024 and is adjustable in Settings.
- Underscore is the filename field separator, so `sanitize()` strips
  underscores from issuer/number values. Keep that invariant.
- The issuer name is cleaned to a short Latin-script brand name (legal suffixes
  like SA/AE/Ltd and labels like TM/AADE removed) — both in the prompt and in a
  local `stripLegalSuffixes` safety net.
- `codesign` fails with "resource fork/detritus" if extended attributes sneak
  into the bundle — `build.sh` runs `xattr -cr` before signing; keep that.
- The "Test Key" button treats any HTTP 2xx as success on purpose: thinking
  models may return no visible text under a tiny token cap.
- `build.sh` and `release.sh` deep-verify the signature
  (`codesign --verify --deep --strict`) and clear xattrs first. Plain
  `codesign -v` is shallow, does not look inside Sparkle.framework, and misses
  exactly the breakage that silently kills auto-updates. Keep both.
